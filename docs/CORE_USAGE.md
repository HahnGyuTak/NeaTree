# NeaTree 파일 처리 코어

Finder 스타일 GUI를 연결하기 위한 Swift 네이티브 코어와 개발용 CLI입니다. 파일 감시·분석 요청·검토 상태·이동·되돌리기를 실제 파일시스템에서 수행합니다. GUI는 같은 서비스를 공유하며 본창과 메뉴바에서 호출합니다.

최신 디자인 요구사항은 [DESIGN_REQUIREMENTS.md](../DESIGN_REQUIREMENTS.md)에 보존합니다. 재사용 가능한 SwiftUI Liquid Glass 컴포넌트와 독립 미리보기 사용법은 [DESIGN_SYSTEM.md](../DESIGN_SYSTEM.md)를 참고하세요. 디자인 미리보기는 샘플 데이터로만 동작합니다.

## 구현된 기능

- 지정 폴더 목록과 파일명 사례 수집, GPT-6.1 Sol을 통한 규칙 후보 분석과 사용자 확정, 확정 규칙 생성·수정·삭제.
- 다운로드 완료 대기, 임시·숨김·미분류 파일 제외, 사용자 지정 확장자·상대 폴더 제외, 직접 파일·폴더 가져오기, 보류 상태 보존.
- 텍스트와 PDF 내용 추출, 이미지·스캔 PDF의 로컬 OCR, 폴더 내부 목록 요약, 읽지 못한 자료와 부분 분석 표시.
- 엄격한 응답 형식의 GPT 분석, 수정 가능한 이름·목적지, 근거와 대안, 수정 내용의 규칙 후보 생성.
- 규칙 변경 후 오래된 제안 적용 거절, 같은 파일의 늦게 도착한 이전 분석 결과 거절.
- 동일 내용 파일 탐색, 이름 충돌 방지, 번호 증가·빈 번호 채우기, 폴더 내부 구조를 유지한 이동.
- 미분류 이동·명시적 재검토, 실제 파일 상태를 확인하는 이동 이력과 되돌리기, 중단된 작업 복구.
- 앱의 편집 초안 영구 저장과 오래된 초안 적용 거절, 다중 선택·공통 목적지·개별 이름 편집과 항목별 결과를 표시하는 일괄 처리.
- API 키의 macOS 키체인 저장. 환경변수 `OPENAI_API_KEY`도 지원하며 키를 문서나 설정 파일에 저장하지 않습니다.

## 실행

macOS 14 이상과 Swift 6 도구가 필요합니다. 이 폴더에서 실행합니다.

```sh
swift build
swift test
swift run organizer help
```

명령은 저장소 루트에서 실행합니다. GUI 앱 번들은 `scripts/pack-app.sh`로 별도 생성합니다.

API 분석 없이 임시 파일로 파일 관리 기능부터 확인할 수 있습니다. `configure`는 지정 폴더의 이름과 구조를 읽어 로컬에 저장합니다. `rules analyze`, `analyze`, `learn`, `watch --analyze`는 선택 범위의 자료를 OpenAI API로 전송합니다.

```sh
swift run organizer --state /원하는/상태저장폴더 configure --downloads /테스트/다운로드 --root /테스트/문서
swift run organizer --state /원하는/상태저장폴더 import /테스트/다운로드/파일.txt
swift run organizer --state /원하는/상태저장폴더 list
```

명령마다 같은 `--state`를 사용합니다. 생략하면 `~/Library/Application Support/FileOrganizer`에 상태를 저장합니다. `catalog` 출력에서 목적지 폴더 ID를 확인하여 `apply <항목 ID> --name <이름> --folder <폴더 ID>`로 적용할 수 있습니다. `apply`와 `unclassified`는 실제 파일을 이동합니다. `history`의 작업 ID를 `undo`에 전달하면 복구합니다.

API 키는 앱의 설정에서 보안 입력란에 입력하거나 **키 파일 가져오기**로 저장합니다. 터미널에서는 `swift run organizer key set`으로 입력할 수 있으며 입력 문자는 화면에 표시되지 않습니다. 채팅이나 명령줄 인자에 키를 넣지 않습니다. `key status`는 설정 여부만 표시합니다.

앱 시작과 `key status`는 Keychain에서 키의 실제 값을 읽거나 인증 창을 띄우지 않고 등록 여부만 확인합니다. 앱의 확인 작업은 메인 스레드 밖에서 실행합니다. 실제 API 작업에서 키를 읽을 때는 macOS의 Keychain 접근 허용이 필요할 수 있으며, 등록 표시는 연결 성공이나 키 접근 권한 검증을 대신하지 않습니다.

저장소 밖에 키 한 줄만 담은 UTF-8 또는 RTF 파일을 준비한 경우 `swift run organizer key import --file <경로>`로 Keychain에 가져올 수 있습니다. 가져오기는 API 호출을 하지 않습니다. 실제 연결은 설정의 **연결 확인** 또는 `swift run organizer api verify --allow-paid-request`로 별도 검증하며, 고정된 합성 자료로 최대 두 번만 요청합니다. CLI에서 지정 파일을 일회성으로 사용하려면 `--key-file <경로>`를 추가합니다. 비용과 검증 범위는 [API 설정 안내](API_SETUP.md)를 확인하세요.

규칙 분석은 `rules analyze`, 후보 확정은 `rules confirm <0부터 시작하는 후보 번호>`, 파일 분석은 `analyze <항목 ID>`를 사용합니다. `learn <항목 ID> --name <수정 이름> --folder <폴더 ID>`는 앞으로 사용할 규칙 후보를 만들며 확정은 별도입니다. `revisit <미분류 항목 ID>`는 이동 후 실제 경로의 파일을 새 검토 항목으로 등록합니다.

확정 규칙은 API 호출 없이 직접 관리할 수 있습니다. 아래 명령에도 앞서 선택한 `--state`를 동일하게 지정합니다.

```sh
swift run organizer --state /원하는/상태저장폴더 rules create --folder '폴더-ID' --instruction '계약서는 날짜_거래처_제목 형식으로 보관'
swift run organizer --state /원하는/상태저장폴더 rules update '규칙-ID' --folder '폴더-ID' --instruction '수정할 규칙 내용'
swift run organizer --state /원하는/상태저장폴더 rules delete '규칙-ID'
swift run organizer --state /원하는/상태저장폴더 exclusions set --extension zip --extension dmg --folder 임시자료
swift run organizer --state /원하는/상태저장폴더 exclusions list
```

`exclusions set`은 두 제외 목록을 통째로 교체합니다. 옵션 없이 실행하면 사용자 지정 제외를 모두 해제합니다. 제외 적용은 파일을 이동하거나 삭제하지 않습니다. 자동 감시로 들어온 미처리 항목은 검토함에서 제외하며, 직접 가져온 현재 파일·보류·완료 이력은 유지합니다. 수동 가져오기 예외는 해당 파일에만 적용되며 같은 경로에 나중에 받은 새 파일로 이어지지 않습니다. 제외 폴더의 대소문자는 다운로드 볼륨의 구분 방식에 맞춰 비교합니다. 규칙 또는 제외 설정이 바뀌면 설정 버전이 변경되어 이전 검토안은 재확인이 필요합니다.

`watch`는 다운로드 감시만 수행합니다. 자동 분석까지 요청하려면 `watch --analyze`를 사용합니다. 종료는 Ctrl+C입니다. 개발용 CLI의 동일 상태 저장소를 여러 프로세스에서 수정하면 저장 충돌을 표시하므로, 감시를 종료한 뒤 별도 명령을 실행합니다. GUI에서는 한 서비스 인스턴스를 공유합니다.

## 현재 범위

동일 볼륨의 일반 파일과 폴더를 지원합니다. 다른 볼륨으로 이동할 때는 원본을 보존한 채 거절합니다. 링크, 앱 패키지와 일부 시스템 위치는 대상에서 제외합니다. 다운로드 안정화 검사에는 항목당 64 MiB·5,000개 노드 한도가 있으며 초과 시 이유를 표시합니다.

`{serial}_`, `{serial}-`, `{serial} `로 시작하는 이름은 같은 폴더의 자리 수와 구분자가 같은 번호를 공유합니다. 예를 들어 `001_계약서.pdf` 다음의 새 견적서는 `002_견적서.txt`가 됩니다. 다른 위치에 번호가 있는 템플릿은 동일한 전체 템플릿끼리 번호를 배정합니다. 번호 자리 수와 빈 번호 사용 정책은 적용 시 명시적으로 선택합니다.

규칙은 현재 목록에 있는 폴더 ID와 비어 있지 않은 지시문으로 저장합니다. 모델에는 확정되어 있고 후보 폴더 목록에 속하는 규칙만 전달합니다. 별도의 조건식·우선순위·상속·충돌 해결 엔진은 아직 없습니다. GUI의 분류 규칙 화면에서 확정 규칙과 후보를 편집·삭제할 수 있습니다. 후보 편집·삭제 전용 CLI 명령은 아직 없습니다.

감시는 다운로드의 바로 아래 파일·폴더를 하나의 단위로 다룹니다. 확장자 제외는 해당 항목의 확장자를 대소문자 구분 없이 비교하며 폴더 내부 파일을 확장자별로 걸러내지 않습니다. 상대 폴더 제외는 와일드카드가 아닌 경로 비교입니다. `프로젝트/임시`처럼 하위 경로를 제외하면 이를 담은 최상위 `프로젝트` 폴더 전체가 자동 감시에서 제외됩니다. 직접 가져오기는 사용자 지정 제외를 우회하지만 링크·지원하지 않는 시스템 위치 등의 안전 검증은 유지합니다.

텍스트는 최대 128 KiB, 폴더 목록은 첫 100개 항목까지 읽습니다. Office 전용 문서 추출은 아직 없습니다. 중복 탐색은 검사 한도와 읽기 실패가 있으면 결과의 `truncated`를 표시합니다.

로컬 OCR은 Apple Vision으로 실행하며 OCR 단계에서 네트워크를 사용하지 않습니다. GPT 분석을 요청하면 추출된 텍스트는 다른 분석 자료와 함께 API로 전송됩니다.

| 대상 | 현재 추출 범위 |
| --- | --- |
| 이미지 | PNG, JPEG, HEIC/HEIF, TIFF, BMP, GIF, WebP. 최대 32 MiB·원본 6천만 픽셀. 여러 이미지/프레임 중 주 이미지만 읽습니다. 실제 디코딩 지원은 macOS ImageIO에 따릅니다. |
| PDF | 최대 64 MiB, 첫 12페이지·총 32,000자. 선택 가능한 텍스트를 우선 읽고 텍스트가 없는 페이지는 최대 3페이지까지 OCR을 시도합니다. 잠긴 PDF는 읽지 않습니다. |
| OCR 렌더링 | 긴 변 최대 2,048픽셀·총 4,194,304픽셀, 결과 최대 32,000자. 한국어·영어를 지원하는 시스템에서는 두 언어를 우선하며 자동 언어 감지를 사용합니다. |

이미지 축소, 추가 프레임 생략, 페이지·문자 한도 또는 일부 페이지 실패가 있으면 `partial_ocr_text`로 표시합니다. 완전히 읽을 수 없거나 텍스트를 찾지 못한 경우에는 `ocr_failed`, `no_text_recognized`, `ocr_limit` 등 이유를 반환합니다. 인식 결과의 철자·숫자 정확성을 보장하지 않으므로 중요한 값은 원본과 대조해야 합니다. 생성한 이미지와 스캔 PDF로 실제 Vision 인식을 확인했습니다.

GUI와 드래그앤드롭, 메뉴바 상주 및 로그인 시 실행 선택을 연결했습니다. 기존 검토 화면의 이름·위치·번호·학습 선택은 `preferences.json`에 검토 당시 파일 지문·제안·설정 버전과 함께 저장되어 재시작 후 복원됩니다. 원본·제안·규칙이 바뀌어도 초안을 자동으로 덮어쓰지 않으며, 다시 검토하기 전에는 적용하지 않습니다.

`OrganizerAppModel`의 `reviewBatch`, `applyBatch`, `holdBatch`, `sendToUnclassifiedBatch`, `undoBatch`는 중복 ID를 제거하고 순차 처리하여 항목별 성공·실패·작업 ID를 반환합니다. 전체를 한 번에 되돌리는 트랜잭션이 아니므로 일부 항목만 성공할 수 있습니다. GUI에서는 ⌘ 또는 ⇧로 파일을 여러 개 선택하고, 개별 이름·목적지를 확인한 뒤 함께 적용·보류·미분류 이동할 수 있습니다. 편집하거나 검토 내용이 달라지면 확인 표시가 해제됩니다. 일괄 적용에는 저장된 최신 검토 초안이 필요하며, 향후 규칙 학습을 선택한 항목은 개별 적용해야 합니다. 정리 이력에서도 여러 항목을 선택해 복원 경로를 확인하고 되돌릴 수 있습니다. CLI 일괄 명령은 아직 없습니다.

승인된 관리 화면 시안에 따라 규칙 편집·감시 제외·일괄 검토를 연결했습니다. 개별 파일의 **원본 미리보기**는 macOS Quick Look으로 엽니다. 프로젝트 관계를 묶어 판단하거나 폴더 내부 파일을 분해해 정리하는 기능은 아직 없습니다.

실제 API 키가 없는 개발 환경에서는 네트워크 모형으로 요청·응답 처리를 검증합니다. 실제 모델의 분류 품질과 계정별 API 접근은 키 설정 후 대표 파일로 확인해야 합니다.

## 검증

다운로드 안정화, 원본 변경과 경로 이탈 거절, API 응답 검증, 오래된 제안 거절, 한글 파일명, 번호 동시 배정, 이동·복구·되돌리기와 동시 탐색을 테스트합니다. 규칙·제외, 초안 복원·일괄 처리, OCR 한도·실패·부분 추출 테스트도 추가했습니다. 최신 통합 실행 결과와 실제 Vision 호출 확인 상태는 [검증 기록](VERIFICATION.md)을 기준으로 확인합니다.

CLI도 별도 임시 폴더에서 보류 상태 복원, 이름 수정과 번호 배정, 중복 탐색, 되돌리기, 미분류와 재검토, 내부 구조를 유지한 폴더 이동의 6개 흐름을 확인했습니다. 이 파일 처리 검증은 합성 파일만 사용했습니다. 실제 API의 별도 검증 결과와 범위는 [API 검증 기록](API_VALIDATION.md)을 확인하세요.

## 구조

`OrganizerService`는 앱 동작을 연결하고, `InboxStore`는 검토 상태를 보존합니다. `CatalogBuilder`와 `FileInspector`가 읽기 자료를 준비하고, `OpenAIClient`와 `PromptLibrary`가 분석을 담당합니다. `MoveEngine`은 허용된 경로·원본 지문·번호 충돌을 검증한 뒤 실행하고 이력을 기록합니다. 파일이 이미 옮겨졌지만 검토함 갱신에 실패한 경우에는 완료된 작업 ID를 명시하며, `reconcile`로 이력을 다시 반영합니다.

비동기 호출에서는 `scanAsync`, `inspectAsync`, `findAsync`를 사용합니다. macOS의 패키지 메타데이터 조회가 Swift 작업 실행을 막지 않도록 별도 DispatchQueue에서 처리합니다.
